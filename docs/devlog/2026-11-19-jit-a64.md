# 2026-11-19 — JIT stage 2: AArch64 code generation

- Added an AArch64 encoder, with every encoding checked against the GNU
  assembler.
- Added a code generator for blocks: simple integer instructions are
  native, the rest call the stage-1 handlers (docs/cpu/jit-a64.md).
- There is no ARM machine here, and installing an emulator (Unicorn) was
  not allowed. So I wrote a strict simulator for the emitted subset
  (tools/a64sim). The differential tests and the Mac OS ROM boot run
  generated code on it. The ROM boot ends bit-identical to the
  interpreter over 1.05 × 10⁹ instructions.
- Pi:
  - Circle maps the heap as not executable, so the 2 MB code buffer is a
    `.text_g3jit` section placed before `_etext`;
  - caches are synchronised after each block is written;
  - `jit = yes` in g3macpi.ini turns it on (off by default);
  - the kernel builds; not yet run on hardware.
- Mistake caught: after the sabotage runs I ran the full suite with a
  binary built from the last sabotaged source and committed. A rebuild
  showed the committed sources pass (352/352). From now on I rebuild
  before every full run.

## Fix: the Pi showed only the rainbow screen

From commit 8a10661 on, the kernel image held the JIT code buffer and grew
past Circle's default kernel limit of 2 MB. Circle puts the boot stack
right after that limit (0x2A0000), which was now inside the kernel
itself. The kernel died at once and only the firmware's rainbow screen
showed. Found on the owner's Pi 400 with the self-test image.

Fix: tools/build-pi.sh configures Circle with --kernel-max-size 8 (stack
now at 0x8A0000; the kernel ends at 0x3C0C28). The build now fails if the
kernel's _end passes the limit. I checked the kernel's size against the
executable range (_etext) but not against the memory map; the size check
now covers that.
