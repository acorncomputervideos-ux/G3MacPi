# 2026-11-19 — booting the Mac OS 9.2.1 install CD

The owner supplied a Mac OS 9.2.1 install CD image (kept in scratch space,
never committed). The CD's own `System Folder:Mac OS ROM` (2,552,522
bytes; newer than the ROM file used so far) was extracted with g3_hfs.

## Fixed on the way

1. **Forth `adler32`** ( adler addr len -- adler' ). The boot script checks
   the image with `1 load-base load-size 14 - adler32` against the number
   in the file's last 12 bytes (`h# 4D446A5F`). This is RFC 1950 Adler-32:
   zlib's value over all but the last 14 bytes matches.
2. **Forth `eval`**: Open Firmware's name for `evaluate`; the script reads
   that number with `['] eval catch`.
3. **Line ends.** The script uses CR alone. `\` comments ran to the next
   LF, i.e. to the end of the script, so everything after the first
   comment was skipped without an error. CR, LF and CR LF now all end a
   line.
4. **CD partition maps.** Apple CDs declare 2048-byte blocks but keep the
   partition map in 512-byte entries with 512-byte units (this CD's HFS
   partition, number 9, starts at 968 × 512). Such maps are now read.
5. **/chosen bootpath.** Mac OS 9.2's loader stops with "MacOS: Boot
   Failure! … unable to find bootpath" without it. The start-up drive
   (`boot = auto|cdrom|disk`, `choose_boot_drive`) now gives
   `/chosen bootpath` = its device path, its first HFS partition and
   `\\:tbxi`, e.g. `/pci@80000000/pci-bridge@d/mac-io@5/ata@20000/disk@0:9,\\:tbxi`,
   in MacSession and the probe.

Each has a unit test, and each fix was sabotaged and caught. The Adler-32
modulus was caught only after a test with long input was added.

## Where it stops now

Mac OS's loader runs, quiesces Open Firmware and starts the nanokernel
and 68K emulator. About 300 ms of 68K start-up code runs, then the ROM's
fatal-error routine at 0xFFC046C0 takes over. It fills a screen area,
prints two hex codes (68K d7, d6), calls one more routine and loops
forever (`BRA.S *` at 0xFFC046EE).

- **Codes:** d7 = 0x0000000F, d6 = 0x0000000C. This assumes the 68K
  emulator keeps d0–d7 in r8–r15 and a7 in r1; it is consistent here:
  d0 = d6 after the last print, and r1 holds 68K stack values. What the
  codes mean is not established yet.
- **Screen:** black. The routine's drawing apparently does not reach our
  framebuffer.
- **Path:** the 68K stack holds return addresses FFC002C6, FFC0E46C,
  FFC0BAE8, FFC04974.

**Tools used:** `G3_SAMPLE_MS` (68K PC in r24), `G3_VDUMP`, and
`G3_SAVE` of physical 0x00C00000 (the 68K ROM at virtual 0xFFC00000),
disassembled with llvm-objdump's m68k target. Its 68K support is
incomplete: no `moveq`, and it crashes on large inputs.

## Following the fatal error (later the same day)

New probe tools:
- `G3_TRACE68=from` (with `G3_TRACE68_TO`, `G3_TRACE68_N`): every change
  of the 68K PC (r24) with d0–d7, a0, a1, a7;
- `G3_MEMWATCH=physaddr`: every change of one byte;
- `G3_MMIO=from,to`: device-register accesses, repeated reads collapsed;
- `G3_REGSAT=pc`: all registers at one address.

These rest on two debugging hooks with tests:
`Ppc750::set_step_hook`, checked once per `run()`, and
`PhysicalBus::set_mmio_trace`, on the device path only.

What they showed:

1. **Error code 12.** The fatal error is "unimplemented trap": the start-up
   routine at 0xFFC0E450 calls OS trap 0x58 (`A458`, with a 22-byte block
   from `A71E` and a routine address at offset 6, the shape of a Time
   Manager task). Trap 0x58 and its neighbours 0x59 and 0x5A still point
   to the ROM's unimplemented-trap handler (0xFFC0E05E). The handler gives
   code 12 to the fatal-error routine (d7 = 0x0F, d6 = 12).
2. **The guard bit is not ours.** The call is guarded by bit 6 of the
   byte at 68K address 0x0DD4, which is physical 0x5DD4 here. The ROM
   writes the 32-bit word there at 0xFFC00162 (0xC301BF46). It comes
   from a record at 0x6404101C, built at 0xFFC0AB78 from the ROM's single
   NewWorld entry (0xFFC0E0B4, chosen because the loader's `Hnfo` block is
   present) and from the loader's info block. The loader writes `Hnfo` and
   version "05" (0x3035) as constants (code at 0x00205250–0x00205294).
   None of this depends on our device tree, so the bit is set on a real
   Blue & White too.
3. **The trap table.** It is filled at 0xFFC0E000 from an offset table in
   the ROM, in which 0x58–0x5A are 0 (unimplemented). Nothing in our run
   writes those slots later. No 68K code stores to the slot or calls
   SetTrapAddress for 0x58. PowerPC code at 0xFFD1AB40 *calls* trap 0x58
   through Mixed Mode; it does not install it.

Open question: what installs the Time Manager traps before 0xFFC002C0 on
real hardware? Probably PowerPC-side code, or a table of native patches,
that our boot does not reach or skips. A reference trace from another
emulator booting the same CD would answer it quickly.

## Reference run in QEMU (owner's go-ahead)

QEMU 9.2.0 (`qemu-system-ppc -M mac99`, OpenBIOS) was built in scratch
space, purely as a reference: none of its code is used. It boots the same
CD. A small gdb-remote-protocol client (scratch, not in the repository)
set write watchpoints on trap-table slots.

- **The same start:** QEMU runs the same trap-table set-up (slot 0x560 =
  0xFFC0E05E, written from 0xFFC0E042) and has the same bit 6 at 0x0DD4
  (0xC301BF06 there, 0xC301BF46 here).
- **The same order, then the gap.** Both boots then install traps
  through SetTrapAddress (68K 0xFFC0DFEA) in the same order: 0x574, 0x1764,
  0x19F8, 0x17FC, 0x14D0, 0x1768, 0x1DA4. QEMU next installs **0x560**:
  0x000B0678, Mixed Mode routine descriptors of the native "TMgr"
  fragment, i.e. **TimeManagerLib**, loaded through StartLib. Ours never
  does; the later timer-task call then hits the unimplemented trap.
- **The library itself is fine.** TimeManagerLib is an LZSS-compressed
  `nlib` in the ROM file's parcels. Our boot decompresses it correctly: a
  Python LZSS decoder (4096-byte window, F = 18, threshold 2) gives the
  same 0x1A34 bytes as our RAM at physical 0x31F70. But none of its code
  ever runs in our boot; in QEMU it does.
- **Where it belongs.** It sits in the "CodePrepare Node Parcel" with
  NVRAMServicesLib and RTCServicesLib, plus an `AAPL,prepare_order`
  property. The other node parcel, "CodeRegister", holds
  NativePowerMgrLib, AGPLib, EtherPrintfLib and StartLib. The rest are
  `prop` parcels keyed by device names: grackle, heathrow-ata, cmd646-ata,
  cuda, via-cuda, mac-io, nvram,flash, uni-north, pmu, ….
- **The working theory:** our boot never performs the CodePrepare step,
  probably because something in our device tree differs from what the
  ROM's StartLib looks for. Next: find what triggers the prepare step.

More probe options: `G3_PC68=lo,hi` (each entry of the 68K PC into a
range), `G3_TRACE68_A7` (freeze when a7 reaches an area), `G3_MMIO_MAX`.
A PVR of 0x00080200 (DingusPPC's MPC750 value) in place of our
placeholder 0x00080000 was tried and changes nothing here.

## Inside the prepare phase

- **The device trees differ:** a dump of QEMU's OpenBIOS tree shows
  PowerMac3,1, uni-north, Keylargo, `ata-3` nodes, an `rtc` node under
  via-cuda and an `nvram` node at the root. Its `/chosen` has nvram and rtc
  handles; ours has nvram (the loader reads it), not rtc.
- **The prepare loop:** the code-prepare loop is 68K code at
  0xFFC01210–0xFFC0129A, before the string `AAPL,prepare_order`. It calls
  the Code Fragment Manager trap `AA5A` twice per library: selector −4,
  then GetSharedLibrary (selector 1) with `'pwpc'` and flag 1.
- **What it does for us:** it handles NativePowerMgrLib, AGPLib, StartLib
  (the CodeRegister group), then Grackle_PCICyclesLib and TimeManagerLib.
  Every call returns 0 (no error). But no TimeManagerLib code ever runs:
  the physical pages executed during that call are kernel, ROM and
  StartLib (container at physical 0x40580), and none of the three copies
  of TimeManagerLib's code in RAM. In QEMU the Time Manager is installed
  from inside that call (68K stack 0x7EF6BC).
- **Imports:** TimeManagerLib imports DriverServicesLib (time-base
  routines), InterfaceLib and PrivateInterfaceLib.

New probe options: `G3_PPAGES=from,to` (physical code pages executed),
`G3_PC68_A1STR` (print the text a1 points to).

## Two causes found: the PowerMgrPlugin and DEC writes

**1. Missing `compatible` on via-cuda.** Breakpoints at the same ROM
addresses in both emulators (CFM's closure walk at 0xFFCE181C, which
reads each connection's state, and the init call at 0xFFCE172C) showed:

- In QEMU the TimeManagerLib closure holds, after the shared libraries,
  PCILib, Math64Lib, DSLGlobalsLib, StartLib, **PowerMgrPlugin**,
  NativePowerMgrLib, DriverServicesLib, and the root TimeManagerLib.
- In ours it ends at a NativePowerMgrLib connection still in state −2
  (not prepared). The walk then returns −2817, so TimeManagerLib's own
  init (data + 0xA8, its loader header) never runs, and trap 0x58 is
  never installed. The same happens for Grackle_PCICyclesLib.
- NativePowerMgrLib imports PowerMgrPlugin (strong import, read from its
  loader section). The Mac OS ROM file's boot code finds it in the
  device tree ("code,AAPL,MacOS,name" = "PowerMgrPlugin", "MacOS: Found a
  PowerPlugin"). The ROM's parcel for Cuda machines (compatible `cuda`,
  device_type `via-cuda`) adds `pef,AAPL,MacOS,PowerPC,register` and that
  name to the matching node.
- Our via-cuda node had no `compatible`. OpenBIOS gives it "cuda". With
  it added, TimeManagerLib's init (code 0x2D8EC) runs, and three more
  library inits follow.

An earlier note here, "CFM attached TimeManagerLib to the wrong
connection", was wrong. It came from reading a transcript vector out of
the end-of-run RAM snapshot, after the memory had been reused. The vector
called at that point is PCILib's init in ROM (0xFFD9100C), a correct
dependency.

**2. DEC writes did not raise the decrementer exception.** Next, Mac OS
sat in the nanokernel's idle task for ever:

- The MESH driver asserts SCSI reset and then waits 40 µs (Duration −40)
  on a kernel timer.
- The kernel's idle loop re-arms an overdue timer by writing DEC =
  0x7FFF0000 and then the old negative value (physical 0xF19200/0xF19204;
  the same pair at 0xF22304/0xF22308), counting on the 0 → 1 change of
  DEC bit 0 to raise the exception.
- We only raised it when counting down, so every timer stopped. QEMU
  models the 750 family's DEC as edge-triggered on writes too
  (`PPC_DECR_UNDERFLOW_TRIGGERED`, hw/ppc/ppc.c), and our CPU now does the
  same (unit test `decrementer_write_edge`, checked by a sabotage run).

**Where it stops now:** System Error 11 (`dsMiscErr`) about 296M
instructions in, both with and without the block cache.

- A 68K routine at 0xFFC4247A restores registers and returns to
  0x07D132D0. That address is on the 68K stack itself: Mixed Mode's switch
  code wrote it there as a frame link (`stw r8,0(r1)` at 0xFFCEEA70).
- The "instruction" there (0xFE02) raises a line-F exception, which ends
  in SysError 11.
- So the 68K stack is out of step by one frame at that return. The
  cause is still to be found.

New probe options:

- `G3_REGSAT_N` / `G3_REGSAT_LR`: one line per hit, optionally only for one
  link register.
- `G3_REGSAT_PATH=n,o1,o2…`: follow pointers from a register, showing
  physical addresses and text.
- `G3_REGSAT=FFFFFFFF,count`: stop at any PC.
- `G3_MTDEC=from`: log decrementer writes.
- `G3_MEMWATCH_MAX`.

## System Error 11 was our display driver; first picture

That SysError 11 was not a stack bug. After the Mixed Mode stub returned,
native code at 0x000DA864 read 0x91000000, and that page was unmapped
(DSI). The kernel's own handler faulted on it again, and the failure
reached the 68K side as `dsMiscErr`. 0x91000000 is our display device's
register block, and the code is our display driver initialising: Mac OS
had mapped neither its registers nor its video memory.

- Mac OS maps a device's memory from the node's PCI `assigned-addresses`
  and gives the driver `AAPL,address`. Our display was a root node with
  physical `reg`, which our driver assumed would be mapped 1:1 (noted as
  unverified in docs/guest/ndrv.md).
- The node now sits under `/pci` with PCI-binding `reg` and
  `assigned-addresses`. The driver falls back to `assigned-addresses`
  instead of `reg`.
- A version with a real PCI configuration space was tried too. It needs
  a vendor ID, so it was dropped: Mac OS maps the device from the tree
  alone, with the same result either way.

Result: Mac OS draws its 50% grey start-up desktop pattern through our
driver, the first picture from the 9.2.1 CD. It then stops about 408M
instructions in with System Error 10 (`dsLineFErr`, a line-F exception),
after a few more Mixed Mode round trips (68K stubs at 0x07D12D80).

New probe option: `G3_REGSAT_PATH=n:offset,...`.

## System Error 10: Mac OS assumes USB; looking for a startup disk

- The line-F error came from USBFamilyExpertLib's init. Inside it,
  USBMassStorageLoader (ROM code at 0xFFE246B4) calls the 68K hook in
  ExpandMem+0x294 with procInfo 2, without a NULL check. In ours the hook
  was 0, and 68K address 0 holds the exception vectors (0xFFC1… decodes as
  line-F).
- In QEMU the hook is 0xFFC2BD20, a ROM 68K component ('INIT', at
  0xFFC07360). The 68K start-up installs it only if bit 2 of low-memory
  byte 0x2408 is set (`BTST #2,$2408`).
- 0x2408 is extValid1 of the ProductInfo record that the Mac OS ROM
  file's loader builds. Its debug output (root `AAPL,debug`) reported
  0000880E for us. The loader ORs in bits from its special-node handlers,
  and bit 26 means "has USB": the same bit makes it report "Virtual
  (USB-emulated) ADB" when no Cuda ADB exists. Its table matches name
  "usb" with device_type "usb".
- A real B&W has USB. We now give the tree a placeholder `/pci/usb` node
  (no registers; no USB controller is emulated yet). extValid1 becomes
  0400880E and the error is gone. Changing the node's type brings the
  error back (sabotage check).

Where it is now: Mac OS shows its grey desktop with the pointer and the
floppy-disk icon it shows while it looks for a startup disk. It does not
take the CD as one. That is next.

Two notes:
- QEMU emulates a PowerMac3,1 (G4), so its machine-ID word and other
  ProductInfo bits differ from ours (B&W: 0x2400 = 42000000 against
  60000000; the SCC ch-a/ch-b `slot-names` bits 23/24). Those
  differences are expected.
- The loader's debug mode (`AAPL,debug` = −1) stops at the end of its
  FCODE on purpose.

## Booting from the CD: "Starting Up…"

Mac OS showed the startup-disk icon and never read the CD itself. Four
fixes, each checked against what Mac OS or QEMU does:

1. **The mac-io base was wrong.**
   - The loader printed "Mac-IO base address = 0x00010000".
   - It takes that base from the *second* entry of mac-io's `reg`. Under
     the PCI binding that entry is BAR 0, but ours had only the
     configuration entry.
   - Every mac-io device's AAPL,address pointed into RAM, so the ATA driver
     probed RAM and found no drives.
   - With the BAR entry the base is 0x80800000, and the driver finds the
     CD drive and talks to it.
2. **READ TOC format 2 (full TOC)** was rejected. It is now answered as
   MMC defines it and QEMU answers it.
3. **The CD was then ejected.** QEMU's command trace (`-trace
   ide_atapi_cmd_*`) shows the same sequence up to the full TOC, then
   reads of the HFS volume. Ours retried every read three times, slowed
   the drive and ejected the disc.
   - The rejected reads were all DMA; PIO reads worked. The ATA request
     block still showed 0x800 bytes left after a DMA read.
   - The reason is the DMA interrupt. Ours was a zero-length pulse, and
     Mac OS's nanokernel acks with bit 31 and dispatches from the *level*
     register, so it never saw input 2. The driver counts DMA bytes in
     that handler.
   - The line now stays up until software acks the source in the PIC, as
     DingusPPC models it. A DMA line held until the channel was next
     written caused an interrupt storm; a 20 µs completion delay in the
     drive turned out to be unnecessary and was removed.
   - Sabotage: without the ack clearing the line, the boot goes back to
     the storm, and the new PIC unit test fails.
4. Mac OS now reads the CD by DMA (1197 DMA commands in the first 6 s) and
   shows **the Mac OS 9.2 "Starting Up…" screen**, with the CD's backdrop
   and extensions loading.

New probe option: `G3_REGSAT_PATH=p<hex>` (32 bytes of physical memory).

## Past "Starting Up…": LocalTalk and the thermal sensor

1. **LocalTalk.** After the start-up screen, Mac OS set up the SCC in
   SDLC mode (WR4 0x20, WR7 0x7E, WR10 0xE0: LocalTalk) and waited for
   ever for its frame to go out; our SCC has no SDLC.
   - QEMU's trace (`-trace escc_mem_writeb_ctrl`) shows only asynchronous
     set-up (WR4 0x44) for the same CD.
   - The difference is extValid1 bits 23/24, which the loader sets when
     the SCC channels have `slot-names` (OpenBIOS gives `slot-names` = 0).
   - With the property, no LocalTalk; four extensions load and the
     progress bar nearly fills.
2. **The thermal assist unit.**
   - Processor-support code (functions CountProcessors, SynchClock,
     IsG3Machine…) walks THRM1's threshold down from 127 °C and waits for
     TIV each time, with interrupts off.
   - We now report TIV/TIN per the MPC750 manual against a fixed 40 °C.
     QEMU's version, from MacOnLinux, uses 24 °C and seems to have TIN's
     sense inverted; we follow the manual.
3. Result: Mac OS switches the display to 1152x870, draws the CD's
   desktop backdrop and the menu bar, and opens a (still empty) window,
   then stays in the nanokernel. That is next.
